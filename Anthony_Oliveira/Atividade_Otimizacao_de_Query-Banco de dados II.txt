-- QUERY 1: O "Caminhão de Lixo" (SELECT * sem restrição e sem limite) 
SELECT * FROM clientes ORDER BY data_cadastro DESC;
Query otimizada:
SELECT id, nome, e-mail FROM clientes ORDER BY data_cadastro DESC;
Limitação do escopo do SELECT permite que a busca possa ignorar campos não relevantes para a busca, diminuindo a quantidade de dados que precisam ser buscados.

-- QUERY 2: Violação da hierarquia de índice (Leftmost Prefix ignorado) -- Cenário: Tabela possui o índice composto (estado, cidade) 
SELECT id_cliente, rua, bairro FROM enderecos WHERE cidade = 'Campinas';
Query otimizada:
SELECT id_cliente, rua, bairro FROM enderecos WHERE estado = ‘São Paulo’ AND cidade = ‘Campinas’
Utilização adequada da hierarquia dos índices, permitindo que o processamento possa percorrer pelos registros indexados corretamente em vez de fazer um full base search.

-- QUERY 3: Junção Tardia com Nested Loop pesado (Falta de filtragem prévia) 
SELECT p.id, c.nome, p.valor_total FROM pedidos p INNER JOIN clientes c ON p.id_cliente = c.id WHERE YEAR(p.data_pedido) = 2026;
Query otimizada:
SELECT p.id, c.nome, p.valor_total FROM pedidos p INNER JOIN clientes c ON p.id_cliente = c.id_clientes WHERE p.data_pedido >= '2026-01-01' AND p.data_pedido <= '2026-12-31';
Ao retirar a função YEAR() da query permite que o otimizador possa percorrer a tabela usando o Index Scan ao invés de fazer uma verificação completa da tabela como antes, consideravelmente melhorando a velocidade da etapa do JOIN, já que o volume de dados retornados será apenas o necessário para a consulta.

-- QUERY 4: Desperdício de Covering Index (Leitura física da tabela sem necessidade) -- Cenário: Tabela possui o índice composto (estado, cidade)
 SELECT * FROM userinfo WHERE estado = 'SP';
Query otimizada:
SELECT estado, cidade FROM userinfo WHERE estado = 'SP'
Mudando a query para que ela utilize o indíce composto durante a consulta, faz com que o banco de dados e a leitura dos dados aconteça usando a estrutura do índice B-Tree, eliminando a necessidade da leitura física de páginas no disco/tabela principal.

-- QUERY 5: A Query Monstro da Capa (Subconsulta correlacionada e DISTINCT desnecessário) 
SELECT DISTINCT c.id, c.nome, SUM(p.valor) AS total_gasto, (SELECT MAX(sp.data_pedido) FROM pedidos sp WHERE sp.id_cliente = c.id) AS data_ultimo_pedido FROM clientes c JOIN pedidos p ON c.id = p.id_cliente WHERE c.data_cadastro >= '2023-01-01' AND c.status = 'ativo' GROUP BY c.id, c.nome ORDER BY total_gasto DESC;
Query otimizada:
SELECT c.id, c.nome, SUM(p.valor) AS total_gasto, MAX(p.data_pedido) AS data_ultimo_pedido FROM clientes c INNER JOIN pedidos p ON c.id = p.id_cliente WHERE c.data_cadastro >= '2023-01-01' AND c.status = 'ativo' GROUP BY c.id, c.nome ORDER BY total_gasto DESC;
A remoção da subconsulta no data_ultimo_pedido elimina o gargalo de I/O e reduz drasticamente a complexidade da query, e adição do DISTINCT resulta em uma etapa extra e desnecessária de ordenação de memória no motor do banco de dados, já que a característica única dos dados já está garantida pelo uso do GROUP BY nos atributos c.id e c.nome 

-- QUERY 6: Produto Cartesiano Velado (CROSS JOIN por falta de condição de junção) 
SELECT p.nome, c.nome_categoria FROM produtos p, categorias c;
Query otimizada:
SELECT p.nome, c.nome_categoria FROM produto p INNER JOIN categorias c ON c.id = p.id_categoria
A consulta original realiza uma junção implícita que combina cada produto com todas as categorias existentes e gera um volume gigante de dados, alterando a query para utilizar explicitamente o INNER JOIN, permite relacionar as tabelas por suas chaves correspondentes, e garante que apenas as combinações válidas entre produto e categoria sejam retornadas, reduzindo drasticamente o consumo de memória e recursos de I/O.

-- QUERY 7: Destruição do uso de índice em Árvore B+ por aplicação de funções no WHERE -- Cenário: Coluna data_criacao possui índice 
SELECT id, status, total FROM faturas WHERE MONTH(data_criacao) = 3 AND YEAR(data_criacao) = 2026;
Query otimizada:
SELECT id, status, total FROM faturas WHERE data_criacao >=  '2026-03-01' AND data_criação <= '2026-03-31'
O uso de funções durante a consulta impede o otimizador do banco de dados de utilizar o índice B-Tree criado, precisando realizar um full table scan, ao substituí-las por um filtro WHERE, deixa o motor do banco de dados usar o índice em data_criacao para realizar um Index Scan, 

-- QUERY 8: Type Mismatch forçando conversão implícita e varredura completa -- Cenário: Coluna codigo_transacao é VARCHAR(36) indexada
SELECT id, valor, status FROM transacoes WHERE codigo_transacao = 9845720194;
Query Otimizada:
SELECT id, valor, status FROM transacoes WHERE codigo_transacao = '9845720194'; 
 A tipagem do atributo codigo_transacao como uma VARCHAR força o banco de dados a realizar uma conversão implícita de tipo em todas as linhas da tabela antes de comparar. Alterando o valor do filtro para o formato de texto ao implementar aspas simples permite que o otimizador utilize o índice do tipo B-Tree criado, reduzindo o tempo de resposta significativamente.

-- QUERY 9: Gargalo de I/O por Subconsultas aninhadas com operador IN 
SELECT id, nome, email FROM clientes WHERE id IN ( SELECT id_cliente FROM pedidos WHERE id_produto IN ( SELECT id FROM produtos WHERE categoria = 'Eletronicos' ) );
Query otimizada:
SELECT cl.id, cl.nome, cl.email FROM clientes cl INNER JOIN pedidos pe ON cl.id = pe.id_cliente INNER JOIN produtos pr ON pe.id_produto = pr.id WHERE pr.categoria =  'Eletronicos'
A consulta original utiliza subconsultas desnecessárias, levando a criação de tabelas temporárias que ocupam espaço na memória e resultam em um alto consumo de I/O. Substituir as subconsultas por operações JOIN utilize os índices das chaves primárias e estrangeiras de forma direta, reduzindo o processamento e a leitura de páginas. 

-- QUERY 10: LEFT JOIN desnecessário limitando o otimizador no Nested Loop 
SELECT c.id, c.nome, p.id AS pedido_id, p.valor_total FROM clientes c LEFT JOIN pedidos p ON c.id = p.id_cliente WHERE p.status = 'faturado' AND p.valor_total > 500;
Query otimizada:
SELECT c.id, c.nome, p.id AS pedido_id, p.valor_total FROM clientes c INNER JOIN pedidos p ON c.id = p.id_cliente WHERE p.status = 'faturado' AND p.valor_total > 500;
O uso do LEFT JOIN impede o otimizador de reordenar as tabelas para escolher o melhor plano de execução. Para otimizá-la, a instrução é alterada para usar o INNER JOIN de forma explícita, Essa mudança fornece um caminho claro ao otimizador do banco de dados, permitindo que ele filtre a tabela pedidos primeiro através de índices em status e valor_total.
