-- QUERY 1: O "Caminhão de Lixo" (SELECT * sem restrição e sem limite) 
SELECT * FROM clientes ORDER BY data_cadastro DESC;
SELECT nome FROM clientes WHERE data_cadastro > 2026-01-01 ORDER BY data_cadastro DESC;
É necessário selecionar as informações que se é desejada para não vir informações desnecessárias, além disso é melhor sempre colocar uma restrição para que a resposta não volte com muitos ítens que não será usado, nesse caso foi colocado para pegar apenas os nomes dos usuários que foram cadastrados no ano de 2026 e a única informação é a do nome, dessa forma a query fica otimizada sem causar problemas de gargalo.

-- QUERY 2: Violação da hierarquia de índice (Leftmost Prefix ignorado) -- Cenário: Tabela possui o índice composto (estado, cidade) 
SELECT id_cliente, rua, bairro FROM enderecos WHERE cidade = 'Campinas';
SELECT id_cliente, rua, bairro FROM enderecos WHERE estado = ‘São Paulo’ cidade = 'Campinas';
No caso de índices compostos é necessário colocar o WERE com o índice exatamente na mesma ordem em que ele foi declarado, dessa forma o SQL entende que a busca deve ser feita usando o índice.

-- QUERY 3: Junção Tardia com Nested Loop pesado (Falta de filtragem prévia) 
SELECT p.id, c.nome, p.valor_total FROM pedidos p INNER JOIN clientes c ON p.id_cliente = c.id WHERE YEAR(p.data_pedido) = 2026;
SELECT p.id, c.nome, p.valor_total FROM pedidos p INNER JOIN clientes c ON p.id_cliente = c.id WHERE p.data_pedido >= '2026-01-01' AND p.data_pedido < '2027-01-01'; 
Com o uso de intervalos de tempo ao invés do “ WHERE YEAR(p.data_pedido) = 2026”, o banco não precisa fazer o cálculo para descobrir se aquela informação está dentro do pedido da query, diminuindo a carga do sistema.

-- QUERY 4: Desperdício de Covering Index (Leitura física da tabela sem necessidade) -- Cenário: Tabela possui o índice composto (estado, cidade)
 SELECT * FROM userinfo WHERE estado = 'SP';
SELECT estado, cidade FROM userinfo WHERE estado = 'SP'; 
Nesse caso pode usar apenas um único termo do índice composto, pois é necessário usar sempre em ordem, mesmo que não seja necessário as outras partes. O uso do “*” faz com que a query procure as informações que estão faltando da tabela do índice (já que ele só tem estado cidade) para retornar a resposta, colocando as informações necessárias no SELECT fica mais leve para o sistema.

-- QUERY 5: A Query Monstro da Capa (Subconsulta correlacionada e DISTINCT desnecessário) 
SELECT DISTINCT c.id, c.nome, SUM(p.valor) AS total_gasto, (SELECT MAX(sp.data_pedido) FROM pedidos sp WHERE sp.id_cliente = c.id) AS data_ultimo_pedido FROM clientes c JOIN pedidos p ON c.id = p.id_cliente WHERE c.data_cadastro >= '2023-01-01' AND c.status = 'ativo' GROUP BY c.id, c.nome ORDER BY total_gasto DESC;
SELECT c.id, c.nome, SUM(p.valor) AS total_gasto, MAX(p.data_pedido) AS data_ultimo_pedido FROM clientes c JOIN pedidos p ON p.id_cliente = c.id WHERE c.data_cadastro >= '2023-01-01' AND c.status = 'ativo' GROUP BY c.id, c.nome ORDER BY total_gasto DESC; 
Não tem necessidade de usar o DISTINCT com o GROUP BY, apenas o segundo comando já garante que venha uma linha por cliente.

-- QUERY 6: Produto Cartesiano Velado (CROSS JOIN por falta de condição de junção) 
SELECT p.nome, c.nome_categoria FROM produtos p, categorias c;
SELECT p.nome, c.nome_categoria FROM produtos p JOIN categorias c ON p.categoria_id = c.id;
Dessa forma evita usar o CROSS JOIN, usando o INNER JOIN que é menos custoso para o sistema.

-- QUERY 7: Destruição do uso de índice em Árvore B+ por aplicação de funções no WHERE -- Cenário: Coluna data_criacao possui índice 
SELECT id, status, total FROM faturas WHERE MONTH(data_criacao) = 3 AND YEAR(data_criacao) = 2026;
SELECT id, status, total FROM faturas WHERE data_criacao >= '2026-03-01' AND data_criacao < '2026-04-01'; 
Dessa forma o uso do índice data_criação é mais eficiente e garante uma resposta mais rápida.

-- QUERY 8: Type Mismatch forçando conversão implícita e varredura completa -- Cenário: Coluna codigo_transacao é VARCHAR(36) indexada
SELECT id, valor, status FROM transacoes WHERE codigo_transacao = 9845720194;
SELECT id, valor, status FROM transacoes WHERE codigo_transacao = '9845720194'; 
Como o codigo_transacao é um varchar usar apenas os números (sem as aspas simples) faz com que o banco não compare de forma correta por conta da diferença de tipos.

-- QUERY 9: Gargalo de I/O por Subconsultas aninhadas com operador IN 
SELECT id, nome, email FROM clientes WHERE id IN ( SELECT id_cliente FROM pedidos WHERE id_produto IN ( SELECT id FROM produtos WHERE categoria = 'Eletronicos' ) );
SELECT DISTINCT c.id, c.nome, c.email FROM clientes c JOIN pedidos p ON p.id_cliente = c.id JOIN produtos pr ON pr.id = p.id_produto WHERE pr.categoria = 'Eletronicos'; 
O uso de JOINs é mais eficiente para esse select, e o uso de DISTINCT garante ter apenas uma linha por cliente, mesmo que esse cliente tenha comprado várias vezes um eletrônico.

-- QUERY 10: LEFT JOIN desnecessário limitando o otimizador no Nested Loop 
SELECT c.id, c.nome, p.id AS pedido_id, p.valor_total FROM clientes c LEFT JOIN pedidos p ON c.id = p.id_cliente WHERE p.status = 'faturado' AND p.valor_total > 500;
SELECT c.id, c.nome, p.id AS pedido_id, p.valor_total FROM clientes c JOIN pedidos p ON c.id = p.id_cliente WHERE p.status = 'faturado' AND p.valor_total > 500; 
Por conta do uso desse WHERE a consulta na prática fica como um INNER JOIN ao invés do LEFT JOIN	que foi colocado, pois um cliente que não tem tenha o status de faturado e um valor total válidos não serão apresentados na resposta da quary, para resolver basta trocar o LEFT JOIN para um INNER JOIN.
